# Тема 5. База данных: PostgreSQL и SQL из кода

> **Организационное примечание.** По расписанию лекция и первый семинар проходят в один день, но их порядок может отличаться. Материал написан так, чтобы быть самодостаточным независимо от порядка.

## Зачем это нужно

Карточки твоей доски лежат в массиве внутри `cards.service.ts`. Ты наверняка уже заметил, чем это плохо: стоит перезапустить сервер — а он перезапускается сам при каждом сохранении файла, — и все созданные карточки исчезают, а на доске снова те же три штуки, что записаны в коде.

Это временное решение, и в прошлой теме мы это прямо проговорили: место хранения известно ровно одному файлу, функции сервиса заранее асинхронные — сервер подготовлен к переезду. Сегодня переезд и состоится.

Хорошая новость: **половину этой темы ты уже знаешь**. SQL — язык, на котором разговаривают с базой данных, — вы проходите в параллельном курсе «SQL. Начальный курс», и `SELECT`, `WHERE`, `JOIN`, `GROUP BY` здесь ровно те же самые. Эта лекция намеренно не повторяет их ни строчкой.

Она про то, что вокруг: как база выглядит, когда запрос к ней пишет не человек в окне тренажёра, а программа.

> [!IMPORTANT] Важно
> Разница не косметическая. В тренажёре запрос набираешь ты, значения для него придумываешь тоже ты, а если ошибёшься — увидишь красную строчку и поправишь. В сервере запрос собирает код, значения в него приходят от постороннего человека через HTTP, а ошибку увидит пользователь в виде сломавшейся доски. Отсюда растут все новые правила этой темы — и параметризованные запросы, и проверка того, что пришло из базы.

**Если ты разберёшься с материалом этой темы, то:**

- Спроектируешь схему из связанных таблиц и опишешь её скриптом, который на чистой базе разворачивается одной командой;
- Подключишь Express к PostgreSQL и научишься писать запросы так, чтобы апостроф в названии карточки ничего не ломал;
- Поймёшь, куда в слоистом сервере кладётся SQL и почему его нельзя писать в контроллере;
- Перестанешь верить на слово типам, которые пришли из базы, и научишься проверять их через Zod;
- Сможешь выполнить несколько запросов по принципу «всё или ничего» — транзакцией.

**Тебе для этой темы нужно помнить:**

- Из курса SQL: `SELECT` со списком столбцов, `WHERE`, `ORDER BY`, первичный и внешний ключ, `NULL`. Если `CREATE TABLE` и `INSERT`/`UPDATE`/`DELETE` в твоём варианте курса ещё не было — ничего страшного, ниже есть короткая шпаргалка;
- Из темы 4: три слоя (роут, контроллер, сервис), правило «чем глубже слой, тем меньше он знает про HTTP», валидация в промежуточной функции;
- Из темы 3: `npm install`, скрипты в `package.json`, импорты своих файлов **с расширением `.ts`**.

## Что переносится из курса SQL, а что меняется

Сначала — успокаивающая часть. Вот что переносится сюда **без единого изменения**:

- `SELECT столбцы FROM таблица WHERE условие ORDER BY столбец` — буква в букву;
- `JOIN` и `LEFT JOIN` между таблицами по внешнему ключу;
- `COUNT`, `SUM`, `AVG`, `GROUP BY`, `HAVING`;
- `INSERT INTO`, `UPDATE ... SET ... WHERE`, `DELETE ... WHERE`;
- сама идея: таблицы, строки, столбцы, первичный ключ, внешний ключ, связь «один ко многим».

Теперь — что меняется:

| Что                         | В курсе SQL                            | Здесь                                                            |
| --------------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| Кто пишет запрос            | ты, руками, в окне тренажёра           | твой код: собирает текст запроса и отправляет его в базу          |
| Откуда берутся значения     | ты набирал их сам                      | приходят в HTTP-запросе от постороннего человека                  |
| Кто видит ошибку в запросе  | ты, сразу, красной строчкой            | пользователь, в виде сломавшейся страницы                         |
| Куда попадает результат     | таблица на экране                      | массив объектов JavaScript, который надо отдать клиенту           |
| СУБД                        | SQLite (файл или онлайн-тренажёр)      | PostgreSQL — отдельная программа-сервер                           |
| Откуда взялись таблицы      | учебная база выдана готовой            | схему проектируешь и создаёшь ты                                  |
| Что бывает при ошибке схемы | ничего, база учебная                   | приложение работает неправильно, а виновата строчка в `CREATE TABLE` |

Последние две строки — самые важные. Дальше по лекции они и разбираются.

### Короткая шпаргалка: то из SQL, что понадобится сегодня

Программа курса SQL у разных направлений немного разная, и часть конструкций могла до тебя не дойти. Всё, что нужно сегодня, — вот в этой таблице; если что-то из неё видишь впервые, читай её внимательно, если всё знакомо — пробегай глазами и иди дальше.

| Конструкция                                             | Что делает                                                   |
| ------------------------------------------------------- | ------------------------------------------------------------ |
| `SELECT id, title FROM cards WHERE is_done = true`       | достаёт строки: какие столбцы, из какой таблицы, по какому условию |
| `INSERT INTO cards (title) VALUES ('Купить хлеб')`       | добавляет одну строку                                        |
| `UPDATE cards SET is_done = true WHERE id = 5`           | меняет значения в найденных строках                          |
| `DELETE FROM cards WHERE id = 5`                         | удаляет найденные строки                                     |
| `CREATE TABLE cards (id INTEGER, title TEXT)`            | создаёт таблицу: перечисляются столбцы и их типы             |
| `PRIMARY KEY`                                            | столбец, который уникально определяет строку — обычно `id`   |
| `REFERENCES users(id)`                                   | внешний ключ: в этом столбце может стоять только тот `id`, который реально есть в `users` |

> [!WARNING] Предостережение
> `WHERE` в `UPDATE` и `DELETE` — не украшение. Без него команда применяется **ко всем строкам таблицы**: `DELETE FROM cards` вычищает доску целиком и без вопросов. В тренажёре это стоило одного перезалива учебной базы; в приложении с настоящими данными это авария. Отменить нельзя.

## Необходимо знать для дальнейшего: четыре слова

### СУБД

> [!NOTE] Определение
> **СУБД** (система управления базами данных) — программа, которая хранит данные и выполняет присланные ей SQL-запросы. «База данных» — это сами данные, СУБД — программа, которая ими заведует.

Если сказать проще: SQLite в тренажёре и PostgreSQL — две разные СУБД. Обе понимают SQL, но устроены по-разному: SQLite — библиотека, работающая с одним файлом на диске, PostgreSQL — отдельная программа, к которой подключаются по сети. Ровно как твой клиент подключается к твоему серверу.

### Схема

> [!NOTE] Определение
> **Схема базы данных** — описание того, из каких таблиц состоит база, какие в них столбцы, какого типа и какие правила на них наложены.

Если сказать проще: схема — это всё, что ты пишешь в `CREATE TABLE`, только про базу целиком. Схема — это про форму данных, а не про сами данные.

### Драйвер

> [!NOTE] Определение
> **Драйвер** — библиотека, через которую программа разговаривает с СУБД: открывает соединение, отправляет текст запроса вместе со значениями и приводит ответ к типам языка. Для Node и PostgreSQL это пакет `pg` (полное название — node-postgres).

Если сказать проще: драйвер — курьер. Он не понимает SQL и не проверяет его: берёт текст, доставляет по адресу, приносит ответ обратно.

### ORM

> [!NOTE] Определение
> **ORM** — библиотека, которая прячет SQL за вызовами на языке программы: вместо `SELECT * FROM cards WHERE is_done = true` пишут что-то вроде `cards.findMany({ where: { isDone: true } })`, а сам SQL библиотека сочиняет за тебя.

Это слово тебе встретится в любой статье про базы и Node, поэтому знать его надо. Но **в этом курсе ORM не используется**, и на то есть причина: SQL ты уже знаешь. Учить поверх знакомого языка ещё один, надстроечный, — это платить дважды. Плюс за ORM непонятно, какой запрос уходит в базу на самом деле, а на этом и ломаются об производительность те, кто начинал сразу с неё.

## PostgreSQL вместо SQLite: шесть отличий, которые ты заметишь сразу

**1. База — отдельная программа, к ней надо подключаться.** У SQLite базой был файл (или вкладка тренажёра). PostgreSQL — программа-сервер: она запускается, слушает порт `5432` и ждёт подключений. Чтобы к ней подключиться, нужны пять вещей — адрес, порт, имя пользователя, пароль и имя базы. Их принято записывать одной строкой:

```
postgres://kanban_user:secret@localhost:5432/kanban
```

Читается по частям: пользователь `kanban_user` с паролем `secret` подключается к машине `localhost` на порт `5432` и работает с базой `kanban`. Формат ровно такой же, как у адреса сайта, — и по той же причине: это адрес.

**2. Типы проверяются по-настоящему.** SQLite к типам относится свободно: текст в столбец `INTEGER` он положит и не поморщится. PostgreSQL так не умеет — попытка положить `"привет"` в целочисленный столбец заканчивается ошибкой. Это не придирчивость, а страховка: испорченные данные ловятся в момент записи, а не через полгода при чтении.

**3. `BOOLEAN` — настоящий тип.** В SQLite «да/нет» изображали числами 0 и 1. В PostgreSQL есть тип `BOOLEAN` со значениями `true` и `false`, и драйвер отдаёт их в JavaScript как настоящие `true`/`false`. Для наших `is_done` и `is_urgent` это именно то, что нужно.

**4. Внешние ключи работают по-настоящему.** В SQLite проверка внешних ключей по умолчанию выключена: можно вставить город с несуществующей страной, и никто не возразит. PostgreSQL такую строку не примет — если в `cards.owner_id` написать `id` пользователя, которого нет, запрос завершится ошибкой. Карточек-сирот в базе просто не появится.

**5. Кавычки различаются по смыслу — и это самая частая ошибка первого дня.**

| Кавычки              | Что означают         | Пример                        |
| -------------------- | -------------------- | ----------------------------- |
| одинарные `'...'`    | строковое значение   | `WHERE title = 'Купить хлеб'` |
| двойные `"..."`      | имя таблицы/столбца  | `SELECT "title" FROM "cards"` |

Написав `WHERE title = "Купить хлеб"`, ты не получишь ноль строк — ты получишь ошибку `column "Купить хлеб" does not exist`. PostgreSQL честно понял двойные кавычки как имя столбца и не нашёл такого. Сообщение при этом звучит загадочно ровно до тех пор, пока не знаешь про эту разницу.

**6. Имена без кавычек приводятся к нижнему регистру.** Столбец, созданный как `isDone`, на самом деле будет называться `isdone`, и запрос `SELECT isDone FROM cards` сработает — потому что и он приведётся к нижнему регистру. А вот в JavaScript в объекте окажется ключ `isdone`, чего ты не ждал.

> [!IMPORTANT] Важно
> Поэтому в SQL действует своё соглашение об именах — **snake_case**: слова пишутся строчными буквами через подчёркивание. `is_done`, `owner_id`, `created_at`, `display_name`. В JavaScript при этом остаётся привычный camelCase: `isDone`, `ownerId`. Два разных мира с двумя разными привычками — и позже в лекции будет отдельный разговор о том, кто именно переводит одно в другое.

Ещё две мелочи, которые пригодятся:

- **`RETURNING`** — приписка к `INSERT`, `UPDATE` и `DELETE`, которая заставляет их вернуть изменённые строки. В SQLite ты про неё не слышал, а здесь она понадобится сразу: клиенту после создания карточки нужен её `id`, а придумывает `id` база.
- **`ILIKE`** — то же, что знакомый `LIKE`, только не различает заглавные и строчные буквы. Для поиска по названию карточки подходит лучше.

Типы, которые понадобятся сегодня, в переводе с того, что было в тренажёре:

| В SQLite (курс SQL)          | В PostgreSQL                        | Комментарий                                    |
| ---------------------------- | ----------------------------------- | ---------------------------------------------- |
| `INTEGER`                    | `INTEGER`                           | целое число                                    |
| `TEXT`                       | `TEXT`                              | строка любой длины                             |
| `REAL`                       | `REAL`, `NUMERIC`                   | дробные числа; `NUMERIC` — для денег           |
| 0 и 1                        | `BOOLEAN`                           | `true` / `false`                               |
| `TEXT` для даты              | `DATE`, `TIMESTAMPTZ`               | настоящие даты, с ними работают функции дат    |
| `INTEGER PRIMARY KEY`        | `INTEGER GENERATED ALWAYS AS IDENTITY` | id, который база придумывает сама           |

## Проектируем схему доски

До сих пор карточка выглядела так:

```typescript
type Card = { id: string; title: string; isDone: boolean; isUrgent?: boolean };
```

Одна сущность, одна таблица — казалось бы, на этом можно и закончить. Но нет: **в схему сразу закладывается таблица пользователей**.

Зачем она нужна прямо сейчас, если входа по паролю в приложении ещё нет? Затем, что владелец карточки — это свойство самой карточки, а не приделанная сбоку функция. Как только в теме 6 появится вход, каждая карточка должна будет знать, чья она. Если заложить владельца сейчас, тема 6 добавит проверку прав — одну строчку в сервисе. Если не закладывать — тема 6 начнётся с переделки всех таблиц и всех запросов разом, и вот это уже дорого.

Итак, две таблицы и связь между ними:

- один пользователь — много карточек;
- у карточки ровно один владелец.

Это связь **один ко многим** — та же самая, что «страна → города» в учебной базе курса SQL. И внешний ключ в ней ставится по тому же правилу: **на стороне «многих»**, то есть в `cards`.

```
users                          cards
─────                          ─────
id            ◄────────────┐   id
email                      └── owner_id
display_name                   title
created_at                     is_done
                               is_urgent
                               created_at
```

### Скрипт схемы

```sql
-- server/db/schema.sql

DROP TABLE IF EXISTS cards;
DROP TABLE IF EXISTS users;

CREATE TABLE users (
  id           INTEGER     GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email        TEXT        NOT NULL UNIQUE,
  display_name TEXT        NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE cards (
  id         INTEGER     GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title      TEXT        NOT NULL CHECK (length(trim(title)) > 0),
  is_done    BOOLEAN     NOT NULL DEFAULT false,
  is_urgent  BOOLEAN     NOT NULL DEFAULT false,
  owner_id   INTEGER     NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX cards_owner_id_idx ON cards(owner_id);
```

Разберём построчно то, чего в курсе SQL могло не быть.

| Конструкция                       | Что означает                                | Что будет, если её не поставить                                                       |
| --------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------- |
| `GENERATED ALWAYS AS IDENTITY`    | `id` придумывает база, по порядку           | придумывать уникальный `id` придётся коду — тем самым `String(Date.now())`, который выдаст одинаковые значения двум запросам в одну миллисекунду |
| `NOT NULL`                        | значение обязательно                        | в таблице появятся карточки без названия, и на доске будут пустые прямоугольники        |
| `UNIQUE`                          | значение не повторяется                     | два пользователя с одной почтой — и в теме 6 будет непонятно, кого из них впускать       |
| `CHECK (...)`                     | своё правило на значение                    | название из одних пробелов пройдёт `NOT NULL` — пробел ведь тоже значение                |
| `DEFAULT false`                   | значение по умолчанию                       | `is_done` придётся передавать в каждом `INSERT`, и однажды его забудут                   |
| `REFERENCES users(id)`            | внешний ключ                                | карточка с несуществующим владельцем; `JOIN` такую строку молча потеряет                 |
| `ON DELETE CASCADE`               | удалили пользователя — удалились его карточки | база просто не даст удалить пользователя, пока у него есть хоть одна карточка          |

> [!IMPORTANT] Важно
> `CHECK (length(trim(title)) > 0)` — это та же проверка на пустое название, которую ты в теме 4 написал в промежуточной функции. Зачем она дважды? Затем, что это две разные линии обороны с разными задачами: проверка в middleware **объясняет пользователю**, что не так, и отвечает кодом 400; проверка в базе **не даёт испортить данные** — и работает, даже если в базу полез кто-то мимо твоего сервера, например ты сам, руками через `psql`. Дублирование здесь намеренное.

> [!WARNING] Предостережение
> `ON DELETE CASCADE` удобен и опасен одновременно: одна строчка `DELETE FROM users WHERE id = 7` уносит с собой все карточки этого пользователя, и подтверждения никто не спросит. Второй вариант — `ON DELETE RESTRICT`: база запретит удалять пользователя, пока у него есть карточки, и удалять их придётся явно. Для доски выбран `CASCADE`, потому что карточка без владельца бессмысленна; для, скажем, бухгалтерских документов выбрали бы `RESTRICT`.

> [!NOTE] Определение
> **Индекс** — вспомогательная структура, которую база строит по столбцу, чтобы искать по нему, не перечитывая таблицу целиком. Как алфавитный указатель в конце книги: без него нужное слово ищут, листая всю книгу подряд, с ним — заглядывают в указатель.
>
> Для `PRIMARY KEY` и `UNIQUE` PostgreSQL строит индекс сам, а для внешнего ключа — **не строит**. Поэтому по `owner_id` индекс добавлен вручную: «все карточки этого пользователя» будет самым частым запросом приложения.

### Почему `created_at`, а не «дата»

`TIMESTAMPTZ` — это «момент времени с часовым поясом». Хранить дату строкой (как приходилось в SQLite) — плохая идея: строки сравниваются как строки, а не как моменты времени, и сортировка по дате начинает выдавать чепуху. Отдельный столбец `created_at` с `DEFAULT now()` стоит почти ничего, а нужен окажется очень быстро: сортировка карточек «новые сверху» — это `ORDER BY created_at DESC`, и без такого столбца её просто не написать.

## Схема как скрипт, а не как последовательность кликов

Таблицы можно создать мышкой в графической программе вроде pgAdmin. Так делать не надо — и вот почему: через неделю ты не вспомнишь, что именно нащёлкал, а преподавателю, соседу по команде и тебе же на другом компьютере нужно получить **ровно такую же** базу. Кликами это не передаётся, а файлом — передаётся.

Поэтому схема живёт в репозитории, обычным текстом, рядом с кодом:

```
server/
  db/
    schema.sql     # какие таблицы существуют
    seed.sql       # немного данных, чтобы доска не была пустой
```

`seed.sql` — «затравка», начальные данные для разработки:

```sql
-- server/db/seed.sql

INSERT INTO users (email, display_name)
VALUES ('anna@example.com', 'Анна');

INSERT INTO cards (title, is_done, is_urgent, owner_id)
VALUES
  ('Спроектировать структуру доски', true,  false, (SELECT id FROM users WHERE email = 'anna@example.com')),
  ('Подключить доску к серверу',     false, true,  (SELECT id FROM users WHERE email = 'anna@example.com')),
  ('Добавить фильтр выполненных',    false, false, (SELECT id FROM users WHERE email = 'anna@example.com'));
```

Обрати внимание на `(SELECT id FROM users WHERE email = ...)` — это тот самый **скалярный подзапрос** из курса SQL, подзапрос, возвращающий одно значение. Он здесь нужен потому, что `id` пользователя придумала база и заранее он неизвестен: жёстко написать `owner_id = 1` можно, но при повторном заливе данных номера сдвинутся, и ссылки поедут.

Разворачивается всё это тремя командами:

```bash
psql -U postgres -c "CREATE DATABASE kanban;"   # один раз
psql -U postgres -d kanban -f db/schema.sql     # создать таблицы
psql -U postgres -d kanban -f db/seed.sql       # налить данных
```

> [!NOTE] Определение
> **`psql`** — консольная программа, которая идёт в комплекте с PostgreSQL и умеет две вещи: выполнить запрос, который ты наберёшь, и выполнить файл со скриптом (флаг `-f`). Это «терминал базы данных».

Последние две команды удобно завести скриптом в `package.json` — тогда сброс базы к исходному состоянию делается одной командой:

```json
"scripts": {
  "dev": "node --env-file=.env --watch index.ts",
  "db:reset": "psql -d kanban -f db/schema.sql && psql -d kanban -f db/seed.sql"
}
```

> [!WARNING] Предостережение
> `schema.sql` начинается с `DROP TABLE` — то есть каждый запуск **стирает все данные** и создаёт таблицы заново. Пока база учебная, это ровно то, что нужно: сломал схему — перезалил и пошёл дальше. Привыкать к этому как к обычной практике не стоит: на базе с настоящими данными такая команда — конец рабочего дня для всей команды.

Порядок `DROP TABLE` тоже не случаен: **сначала дочерняя таблица, потом родительская**. `cards` ссылается на `users`, и пока эта ссылка существует, PostgreSQL не даст удалить `users` — тот самый внешний ключ, который в SQLite не работал, а здесь работает.

> [!NOTE] Определение
> **Миграция** — пронумерованный скрипт с одним изменением схемы («добавить столбец `is_urgent`»), который накатывается на уже существующую базу, не трогая лежащие в ней данные. Инструменты миграций нужны там, где базу нельзя пересоздать, потому что в ней живут настоящие данные.
>
> В этом курсе миграций нет намеренно: наша база учебная, пересоздать её ничего не стоит, а инструмент миграций — это ещё одна библиотека со своими правилами. Знать слово нужно, пользоваться — пока нет.

## Подключаемся из кода: пакет `pg` и пул соединений

```bash
npm install pg
npm install --save-dev @types/pg
```

Как и с Express: сама библиотека — обычная зависимость, типы к ней — в `devDependencies`.

### Что такое пул

> [!NOTE] Определение
> **Соединение** — открытый канал между твоей программой и СУБД. Открыть его небыстро: нужно достучаться до сервера базы, проверить логин и пароль, договориться о настройках.
>
> **Пул соединений** — набор заранее открытых соединений, которые программа переиспользует. Нужен запрос — берётся свободное соединение из набора, выполняется запрос, соединение возвращается обратно.

Если сказать проще: пул — стойка с телефонными трубками, уже дозвонившимися до базы. Надо что-то спросить — берёшь свободную трубку, спросил — кладёшь на место. Без пула каждый запрос начинался бы с набора номера, и на это уходило бы больше времени, чем на сам запрос.

Почему не обойтись одним-единственным соединением на всё приложение? Потому что тогда запросы выстроятся в очередь: пока один пользователь ждёт ответа базы, все остальные ждут его. Пул держит несколько соединений и обслуживает несколько запросов одновременно.

### Один пул на всё приложение

```typescript
// server/db/pool.ts
import { Pool } from "pg";

export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});
```

Три строчки — и это весь файл. Он выполняется один раз при старте сервера, а дальше все репозитории импортируют из него готовый `pool`.

> [!WARNING] Предостережение
> `new Pool()` создаётся **один раз на всё приложение**, а не внутри функции. Написав `const pool = new Pool()` внутри обработчика, ты получишь новый пул на каждый запрос: соединения не переиспользуются, старые не закрываются, и через пару сотен запросов PostgreSQL откажется принимать новые подключения. Признак — сервер работал полчаса и вдруг начал отвечать ошибкой `too many clients already`.

### Пароль не живёт в коде

Строка подключения содержит пароль, поэтому в исходники её не пишут. Её кладут в файл `.env` рядом с `package.json`:

```
DATABASE_URL=postgres://kanban_user:secret@localhost:5432/kanban
```

А Node читает этот файл сам, если запустить его с флагом `--env-file` — как раз он и добавлен в скрипт `dev` выше. Никакой библиотеки для этого ставить не нужно. Всё, что записано в `.env`, оказывается в объекте `process.env`.

> [!WARNING] Предостережение
> `.env` обязан попасть в `.gitignore` — иначе пароль от базы уедет в репозиторий, а из истории Git его потом не вычистить. Рядом кладут `.env.example` с теми же ключами и фиктивными значениями: он коммитится и служит инструкцией — «скопируй в `.env` и подставь свои».
>
> Пока пароль от учебной базы на твоём же компьютере, цена ошибки нулевая. Привычка нужна сейчас, потому что в первый раз, когда цена будет ненулевой, никто не предупредит.

### Первый запрос

```typescript
import { pool } from "./db/pool.ts";

const result = await pool.query("SELECT id, title, is_done FROM cards ORDER BY id");
console.log(result.rows);
```

`pool.query` возвращает не массив строк, а объект результата. Полезного в нём два поля:

| Поле       | Что содержит                                                  |
| ---------- | ------------------------------------------------------------- |
| `rows`     | массив строк; каждая строка — обычный объект JavaScript        |
| `rowCount` | сколько строк затронуто — незаменимо для `UPDATE` и `DELETE`   |

> [!WARNING] Предостережение
> `result` — **не** массив. `result.map(...)` упадёт с `result.map is not a function`, а `result.length` окажется `undefined`. Нужен `result.rows`. Это ошибка первых пятнадцати минут работы с `pg`, и её делают все.

И вторая ошибка тех же пятнадцати минут — забытый `await`. Без него в `result` окажется не результат, а `Promise`, `result.rows` будет `undefined`, а `undefined.map(...)` уронит запрос. Сообщение при этом — `Cannot read properties of undefined` — на настоящую причину не намекает никак.

## Параметризованные запросы

Вот главное новое правило темы. Начнём с того, как делать **нельзя**:

```typescript
// ТАК НЕЛЬЗЯ
const result = await pool.query(`SELECT id, title FROM cards WHERE title = '${title}'`);
```

Выглядит естественно: собрали строку, подставили значение. И работает — ровно до первой карточки с апострофом в названии.

Пользователь создаёт карточку «Прочитать O'Reilly по SQL». Код собирает такой текст:

```sql
SELECT id, title FROM cards WHERE title = 'Прочитать O'Reilly по SQL'
```

Для базы это не название с апострофом. Апостроф закрыл строку, и дальше по тексту идёт что-то непонятное — запрос падает с синтаксической ошибкой, эндпоинт отвечает 500, пользователь видит сломанную доску. Никакого злого умысла: человек просто написал название.

Теперь умысел. Пользователь отправляет вот такое название карточки:

```
'; DELETE FROM cards; --
```

Код собирает вот такой текст:

```sql
SELECT id, title FROM cards WHERE title = ''; DELETE FROM cards; --'
```

Это уже не один запрос, а три команды подряд: найти карточку с пустым названием, **удалить из `cards` всё** и закомментировать оставшийся хвост (`--` в SQL — начало комментария). База честно выполнит их все — она не в состоянии отличить, какая часть текста написана программистом, а какая пришла из формы. Доска пуста, восстановить нечего.

> [!NOTE] Определение
> **SQL-инъекция** — приём, при котором данные, вставленные в текст запроса, становятся его частью и выполняются как команда. Подробно инъекции разбираются в теме 6, вместе с остальной безопасностью; здесь важно, что защита от них — не отдельная мера, а обычный способ писать запросы.

### Как правильно

```typescript
const result = await pool.query(
  "SELECT id, title, is_done FROM cards WHERE title = $1",
  [title],
);
```

`$1` — не подстановка текста. Запрос и значения едут в базу **раздельно**: сначала база получает текст с плейсхолдерами, разбирает его и понимает структуру команды, и только потом получает значения — уже как данные, а не как текст запроса. Значение физически не может стать частью команды, что бы в нём ни лежало: ни апостроф, ни `DELETE FROM`, ни точка с запятой.

Нумерация — по порядку в массиве: `$1` — первый элемент, `$2` — второй. Один и тот же номер можно использовать в запросе несколько раз.

```typescript
await pool.query(
  "UPDATE cards SET title = $1, is_urgent = $2 WHERE id = $3",
  [title, isUrgent, id],
);
```

> [!IMPORTANT] Важно
> Правило простое и не имеет исключений: **всё, что пришло не от тебя, попадает в запрос только через `$1`, `$2`, …**. Ни одна строка из `req.body`, `req.params` или `req.query` не должна оказаться внутри текста запроса — даже если ты «точно знаешь», что там лежит число, даже если поле уже проверено валидацией. Признак нарушения ищется поиском по файлу: **если внутри текста запроса встретился `${` — что-то пошло не так**.

> [!WARNING] Предостережение
> Параметром передаётся **значение**, но не имя таблицы, не имя столбца и не `ASC`/`DESC`. Вот это не сработает:
>
> ```typescript
> await pool.query("SELECT * FROM cards ORDER BY $1", [sortBy]); // сортировки не будет
> ```
>
> Имя столбца — часть структуры запроса, а структуру база разбирает до того, как получит значения. В лучшем случае она откажется выполнять такой запрос («не могу определить тип параметра»), в худшем — поймёт `$1` как обычное строковое значение и отсортирует все строки по одной и той же константе, то есть не отсортирует никак. Если сортировку выбирает пользователь — сверься со списком разрешённого и подставь **своё** проверенное значение:
>
> ```typescript
> const allowedColumns: Record<string, string> = { title: "title", created: "created_at" };
> const column = allowedColumns[sortBy] ?? "created_at";
> const result = await pool.query(`SELECT id, title FROM cards ORDER BY ${column} DESC`);
> ```
>
> Здесь `${column}` безопасен, потому что в нём лежит не то, что прислал пользователь, а одна из двух строк, написанных тобой.

## Куда в слоистом сервере ложится SQL

В прошлой теме сервер разложился на три слоя, и хранилище — массив `cards` — осталось в сервисе. Тогда же было обещано: при переезде на базу менять придётся ровно один файл. Обещание выполняется — вот тот же сервис, только вместо массива в нём запросы:

```typescript
// services/cards.service.ts — первый, наивный вариант
import { pool } from "../db/pool.ts";

export async function getAll(): Promise<Card[]> {
  const result = await pool.query("SELECT id, title, is_done, is_urgent FROM cards ORDER BY id");
  return result.rows;
}
```

Роуты, контроллеры и `index.ts` не изменились ни на строчку — слои разложены правильно. Но задай сервису тот же вопрос, что в прошлой теме задавали одному-файлу-на-всё: **за что он теперь отвечает?**

- за то, что значит операция «получить карточки»;
- за то, каким SQL это делается;
- за то, как строка таблицы превращается в объект приложения.

Три ответственности. И третья — не выдумка ради красоты: строка таблицы и объект, который ждёт клиент, **не совпадают**.

| В таблице               | В приложении                     |
| ----------------------- | -------------------------------- |
| `is_done`, `is_urgent`  | `isDone`, `isUrgent`             |
| `id` — число `1`        | `id` — строка `"1"` (тип `Card`) |
| `owner_id`, `created_at` | клиенту не нужны                |

Написав `return result.rows`, ты отдашь клиенту объекты с полем `is_done`. Клиент читает `card.isDone`, получает `undefined`, и все карточки на доске становятся невыполненными. Ошибки при этом не будет **нигде**: ни сервер, ни браузер не считают это поломкой.

Поэтому появляется четвёртый слой.

> [!NOTE] Определение
> **Репозиторий** отвечает на вопрос **«как достать эти данные из хранилища и как их туда положить»**. В нём живут SQL-запросы и перевод между строкой таблицы и объектом приложения. Нигде больше в проекте SQL не встречается.

Заметь симметрию: контроллер переводит **HTTP ↔ задача**, репозиторий переводит **таблица ↔ объект**. Оба — переводчики на границах приложения, а между ними лежит сервис, который не знает ни про HTTP, ни про SQL и занят только смыслом операций.

| Слой        | Отвечает на вопрос              | Знает про `req`/`res`? | Знает про SQL? |
| ----------- | ------------------------------- | ---------------------- | -------------- |
| Роут        | какие адреса есть               | нет                    | нет            |
| Контроллер  | перевод HTTP ↔ задача           | да                     | нет            |
| Сервис      | что значит операция по сути     | нет                    | **нет**        |
| Репозиторий | как достать и сохранить данные  | нет                    | да             |

> [!IMPORTANT] Важно
> Проверка правильности разложения такая же простая, как в прошлой теме была проверка поиском слова `res` в сервисе: **поиск по проекту слова `SELECT` должен находить его только в файлах репозиториев**. Нашёлся в контроллере или в сервисе — граница сломана.

### Как это выглядит в файлах

```
server/
  db/
    pool.ts                    # пул соединений — один на приложение
    schema.sql                 # какие таблицы существуют
    seed.sql                   # начальные данные
  repositories/
    cards.repository.ts        # SQL про карточки + перевод строка ↔ объект
  services/
    cards.service.ts           # что значит операция
  controllers/
    cards.controller.ts        # перевод HTTP ↔ задача
  routes/
    cards.routes.ts            # какие адреса есть
  middleware/
  types/
```

```typescript
// repositories/cards.repository.ts
import { pool } from "../db/pool.ts";
import type { Card } from "../types/card.ts";

type CardRow = {
  id: number;
  title: string;
  is_done: boolean;
  is_urgent: boolean;
};

function toCard(row: CardRow): Card {
  return {
    id: String(row.id),
    title: row.title,
    isDone: row.is_done,
    isUrgent: row.is_urgent,
  };
}

export async function findAll(): Promise<Card[]> {
  const result = await pool.query(
    "SELECT id, title, is_done, is_urgent FROM cards ORDER BY created_at DESC",
  );
  return result.rows.map(toCard);
}

export async function insert(title: string, ownerId: number): Promise<Card> {
  const result = await pool.query(
    `INSERT INTO cards (title, owner_id)
     VALUES ($1, $2)
     RETURNING id, title, is_done, is_urgent`,
    [title, ownerId],
  );
  return toCard(result.rows[0]);
}

export async function deleteById(id: number): Promise<boolean> {
  const result = await pool.query("DELETE FROM cards WHERE id = $1", [id]);
  return result.rowCount === 1;
}
```

Три вещи здесь стоит рассмотреть отдельно.

**Функция `toCard` — то самое место перевода.** Одна маленькая функция, через которую проходит каждая строка из базы. Именно она превращает `is_done` в `isDone` и число `1` в строку `"1"` — и благодаря ей клиент, написанный ещё в теме 1, продолжает работать без единой правки. Форма таблицы и форма объекта разошлись, и это нормально: примирять их — работа репозитория.

**Столбцы перечислены явно, `SELECT *` не используется.** Причина практическая: `toCard` рассчитывает ровно на эти четыре столбца. Со `SELECT *` в строке появится ещё и `owner_id`, потом `created_at`, а в теме 6 — хеш пароля в таблице пользователей, и он поедет клиенту, потому что никто не заметил. Явный список столбцов — это список того, что репозиторий обещает вернуть.

**`RETURNING` в `INSERT`.** Клиенту после создания карточки нужен её `id`, а придумывает `id` база. Без `RETURNING` пришлось бы делать второй запрос и гадать, какую именно строку искать. С ним `INSERT` сразу отдаёт созданную строку — и она тут же уходит в `toCard`.

А сервис становится совсем тонким:

```typescript
// services/cards.service.ts
import type { Card } from "../types/card.ts";
import * as cardsRepository from "../repositories/cards.repository.ts";

export async function getAll(): Promise<Card[]> {
  return cardsRepository.findAll();
}

export async function create(title: string, ownerId: number): Promise<Card> {
  return cardsRepository.insert(title, ownerId);
}

export async function remove(id: number): Promise<boolean> {
  return cardsRepository.deleteById(id);
}
```

> [!WARNING] Предостережение
> Обрати внимание: `id` в этих функциях стал **числом**, а в теме 4 контроллер передавал в сервис `req.params.id` — строку из адреса. Значит, при переезде на базу контроллер всё-таки придётся тронуть: строку из адреса нужно превратить в число и убедиться, что это вообще число. Делается это не в контроллере руками, а схемой — как именно, разобрано ниже, в разделе про Zod.

> [!NOTE]
> Скажем честно: прямо сейчас сервис выглядит бесполезной прослойкой — три функции, и каждая просто зовёт репозиторий. Так и есть, на этом размере он ничего не добавляет, и в прошлой теме мы отдельно ругали «слои ради слоёв».
>
> Разница в том, что здесь известно, чем он наполнится, и известно точно: в теме 6 в него встанет проверка «а этот пользователь вообще вправе удалять эту карточку». Эта проверка — не про HTTP (в контроллер нельзя) и не про SQL (в репозиторий нельзя). Ей нужен ровно тот слой, который сейчас выглядит пустым.

### Когда база сама говорит «нельзя»

`email` в таблице `users` объявлен как `UNIQUE`. Что произойдёт, если попытаться вставить второго пользователя с той же почтой? Запрос упадёт с ошибкой — и без обработки эта ошибка доедет до обработчика ошибок из темы 3 и превратится в 500 «Что-то сломалось на сервере». Но ничего не сломалось: пользователь просто ввёл занятую почту, и честный ответ здесь — 409.

У каждой ошибки PostgreSQL есть код. Нам понадобятся два:

| Код     | Что означает                                       | Когда встретится                                  |
| ------- | -------------------------------------------------- | -------------------------------------------------- |
| `23505` | нарушено `UNIQUE`                                  | почта уже занята                                   |
| `23503` | нарушен внешний ключ                               | карточка ссылается на несуществующего пользователя |

```typescript
// repositories/users.repository.ts
import { DatabaseError } from "pg";

const UNIQUE_VIOLATION = "23505";

export async function insert(email: string, displayName: string): Promise<User | null> {
  try {
    const result = await pool.query(
      `INSERT INTO users (email, display_name)
       VALUES ($1, $2)
       RETURNING id, email, display_name`,
      [email, displayName],
    );
    return toUser(result.rows[0]);
  } catch (error) {
    if (error instanceof DatabaseError && error.code === UNIQUE_VIOLATION) {
      return null; // почта занята — это не поломка, а ответ
    }
    throw error; // всё остальное — не наше дело, пусть летит наверх
  }
}
```

Дальше работает ровно та же схема, что и с удалением в прошлой теме: **репозиторий сообщает результат возвращаемым значением, а решение о статус-коде принимает контроллер**. `null` от репозитория превращается в контроллере в `409 Conflict` — новый для курса код, означающий «запрос понятен, но противоречит текущему состоянию данных».

> [!WARNING] Предостережение
> В `catch` попадают **все** ошибки, а не только ожидаемая. Строчка `throw error` в конце обязательна: без неё оборванное соединение с базой, опечатка в SQL и переполненный диск одинаково превратятся в «почта занята», и искать настоящую причину ты будешь долго.

## Zod: проверяем и то, что входит, и то, что выходит

В прошлой теме было обещано, что ручные `if` в промежуточной функции заменит библиотека. Она называется **Zod**, и работы у неё здесь две — одна ожидаемая, вторая нет.

```bash
npm install zod
```

### Работа первая: проверка входа

> [!NOTE] Определение
> **Схема Zod** — объект, описывающий требуемую форму данных: какие поля, каких типов, с какими ограничениями. По схеме можно проверить любое значение и получить либо приведённые данные, либо список того, что не так.

```typescript
// validation/card.schemas.ts
import { z } from "zod";

export const newCardSchema = z.object({
  title: z.string().trim().min(1, "Название обязательно и не может быть пустым"),
  ownerId: z.number().int().positive(),
});
```

Это описание читается как предложение: `title` — строка, обрезать пробелы по краям, после обрезки должна остаться хотя бы одна буква; `ownerId` — целое положительное число. Всё, что ты в теме 4 писал руками, здесь укладывается в одну строку на поле — и, в отличие от ручных `if`, ни одно поле нельзя забыть проверить: чего нет в схеме, того не будет и в данных.

Проверка вызывается методом `safeParse`, который **не бросает ошибку**, а возвращает результат:

```typescript
// middleware/validateBody.ts
import type { Request, Response, NextFunction } from "express";
import { z } from "zod";

export function validateBody(schema: z.ZodType) {
  return (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      res.status(400).json({
        error: "Некорректные данные",
        details: result.error.issues.map((issue) => issue.message),
      });
      return;
    }

    req.body = result.data;
    next();
  };
}
```

Две детали, на которые стоит посмотреть внимательно.

**`validateBody` — не middleware, а функция, которая middleware делает.** В теме 4 у тебя была `validateNewCard`, годная ровно для одной проверки; если бы схем стало пять, пришлось бы написать пять почти одинаковых функций. Здесь функция одна, а схема ей передаётся:

```typescript
cardsRouter.post("/", validateBody(newCardSchema), cardsController.create);
```

> [!WARNING] Предостережение
> Обрати внимание на скобки: `validateBody(newCardSchema)` — **со скобками**, потому что в строку роута ставится результат вызова. Забытые скобки (`validateBody` вместо `validateBody(...)`) — типичная ошибка: Express получит функцию, которая ждёт схему, передаст ей `req`, и запрос повиснет навсегда, ничего не ответив и ничего не написав в лог.

**`req.body = result.data`.** После проверки в теле лежат уже приведённые данные — с обрезанными пробелами и без лишних полей. Контроллер, как и раньше, работает с заведомо годными данными и ничего не перепроверяет.

> [!TIP] Совет
> Проверять надо не только тело запроса. `req.params.id` — тоже данные от пользователя: адрес `DELETE /cards/abc` доедет до репозитория, `pg` отправит `"abc"` в целочисленный столбец, и запрос упадёт ошибкой приведения типа — 500 вместо честного 400. Схема для параметров пути пишется так же, а число из строки достаётся через `z.coerce.number().int().positive()`: `coerce` означает «сначала приведи к числу, потом проверяй».

### Работа вторая: проверка того, что пришло из базы

А вот это в курсе новое. Посмотри ещё раз на репозиторий:

```typescript
const result = await pool.query("SELECT id, title, is_done, is_urgent FROM cards");
return result.rows.map(toCard);
```

Вопрос: откуда TypeScript знает, что в `row` есть поле `is_done`? Ответ: **ниоткуда**. `pool.query` возвращает строки типа `any` — «что угодно». Драйвер не читает твой SQL, не знает твоей схемы и честно признаётся, что содержимого строк не знает. А `any` в TypeScript означает «не проверяй здесь ничего»: `row.is_done`, `row.isDone` и `row.какая_угодно_чушь` компилятор пропустит одинаково.

Чем это оборачивается на практике: кто-то правит запрос и случайно убирает из списка столбцов `is_done`. Ни TypeScript, ни база не возражают — запрос корректен. `row.is_done` становится `undefined`, `toCard` кладёт `isDone: undefined`, клиент получает карточки без признака выполнения, и фильтр в шапке перестаёт работать. Ошибки нет нигде — есть тихо неправильно работающее приложение.

Значит, строку из базы надо проверять так же, как данные от пользователя:

```typescript
// repositories/cards.repository.ts
import { z } from "zod";

const cardRowSchema = z.object({
  id: z.number(),
  title: z.string(),
  is_done: z.boolean(),
  is_urgent: z.boolean(),
});

function toCard(row: unknown): Card {
  const parsed = cardRowSchema.parse(row);

  return {
    id: String(parsed.id),
    title: parsed.title,
    isDone: parsed.is_done,
    isUrgent: parsed.is_urgent,
  };
}
```

Отдельный тип `CardRow` теперь не нужен: `parse` возвращает уже проверенное и типизированное значение — тип Zod выводит из самой схемы. Описание формы строки существует в проекте в одном экземпляре и работает сразу и как проверка, и как тип.

> [!IMPORTANT] Важно
> Здесь стоит `parse`, а не `safeParse` — и это осознанный выбор. Негодные данные от пользователя — обычное дело, на них отвечают кодом 400. Негодная строка **из собственной базы** — это сломанный запрос или разъехавшаяся схема, то есть ошибка программиста. Такое не «обрабатывают»: `parse` бросает ошибку, она долетает до обработчика ошибок из темы 3, сервер отвечает 500 и пишет причину в лог — ровно то, что нужно, чтобы поломку заметили и починили, а не замаскировали.

### Что `pg` возвращает не тем типом, какой ты ждёшь

Ещё одна причина проверять выход из базы: типы PostgreSQL и типы JavaScript совпадают не всегда.

| Тип в базе                 | Что приходит в JavaScript | Комментарий                                       |
| -------------------------- | ------------------------- | -------------------------------------------------- |
| `INTEGER`, `BOOLEAN`, `TEXT` | число, `boolean`, строка | как ожидается                                      |
| `COUNT(*)` и `BIGINT`      | **строка** `"3"`          | большое целое не помещается в число JavaScript без потерь, поэтому драйвер отдаёт его строкой |
| `NUMERIC`                  | **строка**                | по той же причине: точность важнее удобства        |
| `TIMESTAMPTZ`              | объект `Date`             | не строка; клиенту его отдают через `.toISOString()` |

Вторая строчка таблицы ловит почти всех: код `const total = result.rows[0].count; return total + 1;` возвращает `"31"` вместо `32`, потому что `+` со строкой — это склейка. Лечится приведением: `Number(result.rows[0].count)` — или, если результат идёт через схему, `z.coerce.number()`.

## Транзакции

> [!NOTE] Определение
> **Транзакция** — несколько запросов, выполняемых как одно целое: либо выполняются все, либо не выполняется ни один.

Хрестоматийный пример — перевод денег: списать со счёта отправителя и зачислить на счёт получателя. Если между этими двумя запросами оборвётся связь или упадёт сервер, деньги исчезнут. Транзакция не даёт остаться в середине: либо оба запроса, либо ни одного.

В доске такой случай тоже есть. При регистрации пользователя мы хотим не только завести запись в `users`, но и создать ему стартовую карточку «Добро пожаловать» — чтобы доска не встречала новичка пустотой. Это два `INSERT`, и если второй упадёт, останется пользователь в состоянии, которого мы не задумывали. Пока цена невелика, но в теме 6 к регистрации добавится ещё и запись роли, и полууспешная регистрация станет настоящей проблемой.

Команд три, и они те же самые в любой СУБД:

| Команда    | Что делает                                            |
| ---------- | ------------------------------------------------------ |
| `BEGIN`    | начать транзакцию                                     |
| `COMMIT`   | зафиксировать всё сделанное                           |
| `ROLLBACK` | отменить всё сделанное с момента `BEGIN`              |

> [!IMPORTANT] Важно
> Транзакция живёт внутри **одного соединения**. А `pool.query()` каждый раз берёт из пула любое свободное соединение — три вызова подряд спокойно могут уйти по трём разным, и тогда `BEGIN` окажется в одном соединении, `INSERT` — в другом, а `COMMIT` — в третьем. Транзакции не получится, при этом **ошибки тоже не будет**: всё «сработает», просто откатывать в случае беды будет нечего.

Поэтому для транзакции соединение берут из пула явно и все запросы шлют в него:

```typescript
// repositories/users.repository.ts
export async function registerWithWelcomeCard(
  email: string,
  displayName: string,
): Promise<User> {
  const client = await pool.connect();

  try {
    await client.query("BEGIN");

    const userResult = await client.query(
      `INSERT INTO users (email, display_name)
       VALUES ($1, $2)
       RETURNING id, email, display_name`,
      [email, displayName],
    );
    const userRow = userResult.rows[0];

    await client.query(
      "INSERT INTO cards (title, owner_id) VALUES ($1, $2)",
      ["Добро пожаловать на доску", userRow.id],
    );

    await client.query("COMMIT");
    return toUser(userRow);
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}
```

Обрати внимание на `pool.connect()` вместо `pool.query()`: это и есть «взять из пула конкретную трубку и держать её в руках, пока не закончу».

> [!NOTE] Определение
> **`finally`** — блок, который выполняется в любом случае: и когда `try` дошёл до конца, и когда выбросил ошибку. Именно поэтому `client.release()` стоит в нём: соединение обязано вернуться в пул, чем бы дело ни кончилось.

> [!WARNING] Предостережение
> Забытый `client.release()` — самая коварная ошибка этой темы. Соединение не возвращается в пул, и через несколько таких запросов свободных не остаётся. Сервер при этом **не падает** — он просто перестаёт отвечать, вечно дожидаясь соединения, которое уже никогда не освободится. В логах при этом пусто, и ищут такую поломку долго.

> [!TIP] Совет
> Транзакция нужна не всегда. **Один запрос уже атомарен сам по себе**: `UPDATE cards SET is_done = $1 WHERE id = $2` либо выполнится целиком, либо не выполнится вовсе, и оборачивать его в `BEGIN`/`COMMIT` бессмысленно. Транзакция нужна ровно тогда, когда запросов **несколько** и промежуточное состояние между ними недопустимо.

## Врезка: SQL и агент

Агент пишет SQL быстро и обычно правильно — сложить `JOIN` из четырёх таблиц он умеет лучше, чем ты сегодня. Проверять за ним всё равно надо, но проверять есть смысл не «весь код вообще», а пять конкретных вещей. Это полминуты, и они отсекают почти все типовые проблемы:

1. **Значения передаются через `$1`, а не склейкой строк** — смотришь на это первым делом, всегда;
2. **В `UPDATE` и `DELETE` есть `WHERE`** — агент, увлёкшись задачей «очистить статус», вполне может обновить всю таблицу;
3. **Столбцы в `SELECT` перечислены явно** и ровно те, которые разбирает функция перевода;
4. **`client.release()` стоит в `finally`**, если появилась транзакция;
5. **SQL не просочился в сервис или контроллер** — поиск по слову `SELECT` показывает только файлы репозиториев.

Отдельно: агенту стоит **сразу давать текст `schema.sql`** в контексте задачи. Не получив схему, он додумает имена столбцов по здравому смыслу — напишет `done` вместо `is_done` и `user_id` вместо `owner_id`, — и код будет выглядеть безупречно ровно до первого запуска.

---

## Частые ошибки новичков

- **Значение вставлено в текст запроса склейкой строк** — апостроф в названии роняет запрос, а недобрый пользователь роняет таблицу. Ищется поиском `${` внутри текста запроса;
- **Забыт `WHERE` в `UPDATE` или `DELETE`** — команда применилась ко всем строкам таблицы; отменить нельзя;
- **Строка написана в двойных кавычках** — `column "Купить хлеб" does not exist`; строки в SQL — только в одинарных;
- **Столбец назван в camelCase** — база привела имя к нижнему регистру, и в объекте оказалось `isdone` вместо ожидаемого `isDone`;
- **Забыт `.rows`** — `result.map is not a function`, потому что `result` не массив;
- **Забыт `await`** — в `result` лежит `Promise`, `result.rows` равно `undefined`, а сообщение об ошибке про настоящую причину не говорит ничего;
- **`new Pool()` создаётся внутри функции** — новый пул на каждый запрос, соединения кончаются, база отвечает `too many clients already`;
- **Забыт `client.release()`** — сервер тихо перестаёт отвечать, в логах пусто;
- **Транзакция собрана из `pool.query()`** — три команды ушли по трём соединениям, транзакции нет, ошибки тоже нет;
- **`SELECT` найден в сервисе или контроллере** — граница слоёв сломана;
- **`return result.rows` прямо клиенту** — уезжают `is_done` вместо `isDone` и `owner_id`, который клиенту вообще не предназначен;
- **`SELECT *` в репозитории** — сегодня работает, а после добавления столбца в схему клиент получает лишнее, и никто этого не замечает;
- **От `COUNT(*)` ждут число** — приходит строка, и `+ 1` превращается в склейку;
- **`.env` закоммичен вместе с паролем** — из истории Git его уже не вычистить;
- **Порядок `DROP TABLE` перепутан** — родительскую таблицу удаляют раньше дочерней, и внешний ключ не даёт этого сделать;
- **`id` из адреса не проверен** — `DELETE /cards/abc` уходит в базу и возвращает 500 вместо честного 400.

## Заключение

Собери тему в одну картину:

- SQL из курса-соседа переносится сюда без изменений — меняется не язык, а то, кто пишет запрос, откуда в нём берутся значения и кто увидит ошибку;
- PostgreSQL, в отличие от SQLite, — отдельная программа-сервер, которая по-настоящему проверяет типы и внешние ключи; строки в ней пишутся в одинарных кавычках, а имена столбцов — в snake_case;
- Схема проектируется сразу с таблицей пользователей: владелец карточки — её свойство, а не функция, которую можно приделать потом;
- Схема живёт скриптом в репозитории (`schema.sql` + `seed.sql`), а не последовательностью кликов в графической программе;
- К базе подключаются через пул соединений — один `Pool` на всё приложение, строка подключения в `.env`, `.env` в `.gitignore`;
- Всё, что пришло от пользователя, попадает в запрос **только** через `$1`, `$2`, … — это и защита от инъекций, и просто единственный способ, при котором апостроф в названии не ломает запрос;
- SQL живёт ровно в одном слое — в репозитории, который переводит строку таблицы в объект приложения, как контроллер переводит HTTP-запрос в задачу;
- Zod проверяет данные на обеих границах: то, что пришло в API, — через `safeParse` и ответ 400, и то, что пришло из базы, — через `parse`, потому что `pg` отдаёт строки типа `any` и TypeScript здесь не помогает ничем;
- Транзакция нужна, когда запросов несколько и промежуточное состояние недопустимо; она требует одного соединения, взятого через `pool.connect()`, и `client.release()` в `finally`.

Доска наконец переживает перезапуск сервера — а таблица `users`, которая сегодня выглядит почти декоративной, в следующей теме окажется главной: к ней добавятся пароль и роль, вход по токену и правило «свою карточку удалять можно, чужую нельзя». И там же выяснится, зачем на самом деле нужен был сервис, который сегодня только и делал, что пересылал вызовы в репозиторий.

- Документация PostgreSQL, приложение с кодами ошибок: https://www.postgresql.org/docs/current/errcodes-appendix.html — сюда идут, когда в логе появился незнакомый пятизначный код;
- Документация Zod: https://zod.dev/ — начать стоит с разделов `Objects` и `Parsing`;
- PostgreSQL Tutorial: https://www.postgresqltutorial.com/ — короткие статьи с примерами по каждой конструкции (англ.);
- «Use The Index, Luke!»: https://use-the-index-luke.com/ru — про индексы человеческим языком, без теории алгоритмов; читается как книга;
- Билл Карвин, «Программирование на SQL. Изучаем антипаттерны» — сборник типовых ошибок проектирования схемы; полезно читать после того, как спроектируешь первую схему сам.
